# CactusGuard v0.5.0 — Notas da versão

**Data:** 2026-11-09 · **Tipo:** beta interna (não comercial) · **Banco:** migration V50 · **Roadmap:** `specs/048` (Fases 0 e 1 concluídas)

## 1. Para quem é esta versão
Demonstração controlada, testes internos e homologação técnica com parceiros. **Não usar com dados reais de clientes em
produção** antes das Fases 2–5 (ver §5).

## 2. Verificação desta versão
| Projeto | Comando | Resultado esperado |
|---|---|---|
| Backend | `cd cactusguard-backend && JAVA_HOME=/c/Java/jdk-25.0.2 ./mvnw verify` | EXIT=0 (unit + ITs PostgreSQL/Kafka com Testcontainers) |
| Web | `cd cactusguard-web && npm run typecheck && npm run lint && npm test -- --run && npm run build` | EXIT=0 em cada |
| Mobile | `cd cactusguard-mobile && flutter analyze && flutter test` | EXIT=0 em cada |

## 3. Como subir (desenvolvimento)
Infra local (administrada fora do repositório): PostgreSQL 17 `127.0.0.1:5432/cactusguard` (`app_user`/`app_password`),
Redis `127.0.0.1:6379`, Kafka 3 nós `127.0.0.1:19092,29092,39092`.

```bash
cd cactusguard-backend && ./mvnw spring-boot:run      # perfil dev; Flyway aplica até V50
cd cactusguard-web && npm install && npm run dev       # ou npm run dev:mock (sem backend)
cd cactusguard-mobile && flutter run --dart-define=USE_MOCK=true
```
Usuários de dev: ver tabela no `README.md` (admin, analista, supervisor, supervisor2, auditor, analista2/demo2, platform).

## 4. Atualização de um ambiente existente (obrigatório ler antes)
1. **Backup do banco.** As migrations V33–V50 adicionam `tenant_id` a todas as tabelas, convertem 63 FKs para compostas e
   **reconstroem `transactions` como tabela particionada** (cópia em uma transação — em bases muito grandes, planejar janela
   ou migração em lotes; a V43 falha se houver linha com `tenant_id` diferente do pai).
2. **Dois papéis de banco** em produção: dono do schema para o Flyway (`SPRING_FLYWAY_USER/PASSWORD`) e papel de runtime
   `NOSUPERUSER NOBYPASSRLS` não-dono (`CACTUS_DB_USERNAME/PASSWORD`). Com superusuário o RLS **não** é aplicado.
3. **Variáveis obrigatórias fora de dev/test** (a aplicação não sobe sem elas): `JWT_SECRET` (≥ 32 bytes),
   `ENCRYPTION_KEYS` (`v1:<base64 32 bytes>`), `DOCUMENT_HASH_KEY` (≥ 32 caracteres), `SPRING_PROFILES_ACTIVE=prod`.
   Recomendadas: `CORS_ALLOWED_ORIGINS`, `CACTUS_TRUSTED_PROXIES`, `CACTUS_KAFKA_*`, `CACTUS_OTEL_*`. Lista completa em
   `specs/047` e `docs/engenharia/ci-cd.md`.
4. **Recalculo de hashes**: na primeira subida, os hashes de documento são migrados automaticamente para chave por tenant
   (busca por CPF/CNPJ pode falhar durante a migração daquele tenant). Usuários precisam **logar novamente** (refresh
   tokens passaram a ser armazenados como hash).
5. Kafka: tópicos são criados pela aplicação (RF 3) salvo `CACTUS_EVENTS_TOPICS_CREATE=false` (tópicos via IaC).

## 5. Limitações conhecidas (honestas — impedem uso comercial)
| Área | Limitação | Plano |
|---|---|---|
| Motor de decisão | Sem API de decisão síncrona (< 100 ms) para fraude PIX; regras ainda em Java (sem builder no-code, backtesting e shadow mode) | Fase 2 — spec 049 |
| Desempenho | Consultas por janela de 30 dias levam 150–400 ms (inviável no caminho síncrono); teste de volume foi de execução única, não p95 real | Feature store em Redis (Fase 2); teste de carga (Fase 5) |
| Inteligência | Screening sem matching fuzzy calibrado; sem listas brasileiras automáticas (PEP CGU, CEIS/CNEP); sem grafo de vínculos nem ML | Fase 3 |
| SISCOAF | Provedor real não validado contra o leiaute oficial do COAF | Fase 4 + validação jurídica |
| Relatórios regulatórios | AIR e relatório de efetividade ainda não gerados a partir dos dados | Fase 4 |
| Mobile | Só fundação (telas de negócio pendentes); nada nativo testado em aparelho; APK não gerado; fuso fixo UTC-3 | Fase 2/4 |
| Push | Envio real desligado (sem projeto Firebase) | Quando houver Firebase |
| API | 4 endpoints ainda serializam entity (endereços, histórico de risco, notificações, watchlist); documento de UBO via query string; prazo de alerta/SISCOAF calculado no front | Dívidas da Fase 2 |
| Contas | Senha temporária sem troca obrigatória no primeiro acesso | Dívida da Fase 2 |
| Auditoria | Âncoras da cadeia de hash só no próprio banco (precisa armazenamento WORM externo) | Fase 5 |
| CI/CD | Workflows nunca executados no GitHub; ruleset da `main` não configurado | Ação do dono do repositório |
| Conformidade | Sem pentest, ISO 27001/SOC 2, DR testado | Fase 5 |

## 6. Pendências de validação jurídica/compliance
